# 分镜图视觉 QA 的 Token 消耗与优化方案

## 问题背景

当前 skill 在生成分镜图后，要求助手检查实际图片，并记录 QA 结果。主要检查内容包括：

- 是否恰好包含四个画面；
- 四格内容是否符合已确认的分镜计划；
- 产品身份、数量、结构、颜色和材质是否正确；
- 手部是否存在畸形、穿模或不合理动作；
- 四格之间的动作或剪辑关系是否合理；
- 标签、时间和画面顺序是否正确；
- 是否存在水印、乱码、多余文字或严重变形。

视觉 QA 可以避免把明显错误的图片直接交付给用户，但如果重复查看多张相似图片，也可能增加不必要的图像理解 token 消耗。

## Token 消耗来自哪里

写入简短的 QA 结果本身消耗很低，例如：

```json
{
  "qa": {
    "result": "pass",
    "notes": []
  }
}
```

主要消耗来自助手读取和分析图片，尤其是以下情况：

1. 检查无标签四宫格原图；
2. 分别检查四张拆分面板；
3. 检查添加标签后的审核图；
4. 再次检查冻结后的最终图；
5. 每次检查都重新描述完整画面；
6. 因轻微问题自动重试并重新检查。

如果每个镜头都重复读取原图、四张面板图和最终图，多个镜头累计后可能产生明显的 token 消耗。

## 优化原则

视觉 QA 应保留，但需要遵循以下原则：

- 确定性问题交给脚本检查；
- 助手只判断脚本无法理解的视觉问题；
- 默认只视觉检查最终审核图一次；
- QA 结果保持简洁，不重复描述完整分镜；
- 小问题交给用户决定，不自动重试；
- 只有发现问题时，才按需回看原始图或单独面板。

## 脚本负责的检查

以下内容不需要助手通过视觉理解判断，应由脚本自动校验：

- 图片文件是否存在；
- 输出图片是否为 9:16；
- 是否有且只有 4 条面板记录；
- `top_left`、`top_right`、`bottom_left`、`bottom_right` 是否各出现一次；
- 四段时间是否连续并覆盖完整时长；
- 四格排列顺序是否正确；
- 标签文字是否来自 `shot.json`；
- 标签时间是否与项目设置一致；
- 参考图和产物哈希是否变化；
- 输出版本是否覆盖已有文件；
- 面板路径是否逃出项目目录；
- 批准记录是否仍绑定当前输入和产物。

这些检查应在排版和工作流脚本中完成，不消耗图像理解 token。

## 助手负责的检查

助手默认只查看最终的：

```text
storyboard-review-vNN.png
```

视觉检查以下内容：

- 是否仍然是用户提供的产品；
- 产品数量是否正确；
- 产品结构、配件和主要图案是否明显错误；
- 四格内容是否符合已确认的四句画面说明；
- 手部是否存在明显畸形、穿模或异常手指；
- 动作是否符合产品真实结构；
- 连续动作是否能够合理衔接；
- 剪辑序列是否围绕同一个表达目的；
- 标签是否遮挡产品重点；
- 是否存在水印、乱码、多余文字或明显生成错误。

## 默认低消耗流程

```text
生成无标签四宫格
→ 脚本检查文件、尺寸、面板数据和版本
→ 脚本拆分四格并添加准确标签
→ 助手查看最终审核图一次
→ 写入简短 QA 结果
→ 提交用户审核
```

默认不要求助手分别查看四张拆分面板。

## 什么时候需要回看原始图片

只有出现以下情况时，才查看原始无标签四宫格或单独面板：

- 最终审核图出现疑似裁切问题；
- 标签遮挡导致无法判断原始画面；
- 四格排列顺序可能错误；
- 排版后的画面与原始生成结果不一致；
- 需要判断问题来自图片生成还是后期排版；
- 用户明确要求查看原始图；
- 严重缺陷需要进一步定位。

## QA 结果格式

### 完全通过

```json
{
  "qa": {
    "result": "pass",
    "notes": []
  }
}
```

### 存在轻微问题但可以审核

```json
{
  "qa": {
    "result": "pass_with_notes",
    "notes": [
      "第四格丝带颜色比参考图略浅"
    ]
  }
}
```

### 存在严重问题

```json
{
  "qa": {
    "result": "failed",
    "notes": [
      "第三格产品结构与参考图明显不符",
      "第四格手部出现异常手指"
    ]
  }
}
```

QA 说明应简短记录具体问题，不重复输出完整的四格画面描述。

## QA 与用户批准的区别

助手记录：

```json
"result": "pass"
```

只表示没有发现明显的客观问题，不代表用户已经批准。

视觉 QA 通过后，镜头仍应进入：

```text
storyboard_review_pending
```

只有用户明确表示“通过”“这张可以”或其他等价表达后，才能：

- 冻结最终分镜；
- 写入批准记录；
- 进入视频提示词阶段；
- 或在仅分镜图交付时标记完成。

## 重试规则

QA 发现问题后不得自动重新生成。

处理方式：

```text
没有明显问题
→ pass
→ 提交用户审核

有轻微问题但仍可使用
→ pass_with_notes
→ 告知用户，由用户决定是否接受

存在严重结构错误
→ failed
→ 停止，等待用户决定是否重新生成
```

只有用户明确要求重新生成时，才记录重试原因并分配新版本。

## 建议写入 Skill 的规则

> 默认只对最终 `storyboard-review-vNN.png` 进行一次简洁视觉 QA。尺寸、面板数量、时间范围、路径、哈希、标签内容和版本覆盖由脚本检查。助手只判断产品一致性、结构、手部、动作合理性、画面对应关系、标签遮挡和明显生成缺陷。仅在发现裁切、排序或生成问题时，按需查看原始四宫格或单独面板。QA 结果保持简短，且不得因轻微问题自动重试。

## 预期效果

采用该方案后，可以：

- 保留必要的交付质量检查；
- 减少对同一图片的重复视觉分析；
- 降低多个镜头累计的图像理解 token 消耗；
- 避免助手输出无用的长篇 QA 描述；
- 保留用户对轻微偏差的最终决定权；
- 防止因自动重试产生更高的图片生成和审核成本。

## 后续实施建议

该问题可以先作为流程优化项保留。后续修改 skill 时，重点调整：

1. `SKILL.md` 中的视觉 QA 要求；
2. `references/execution.md` 中的生成后检查流程；
3. `shot.json` 的 QA 记录规范；
4. 排版和工作流脚本中的确定性检查；
5. 测试“默认只需检查最终审核图”的行为；
6. 确保严重失败仍然停止并等待用户决定。
