# Batch Storyboard Video Prompts

Create product storyboards using the user's photos and [prompt reference](references/prompt-templates.md). Before operating project files or generating an image, read [execution.md](references/execution.md) for the commands and artifact contract.

## Scope and review mode

- Quantity omitted means **one storyboard image**, regardless of the number of reference photos. One image contains four panels; four panels do not mean four separate deliverables.
- One image stays in the current conversation. For two or more images in staged mode, use a coordinator conversation and separate shot conversations; read [hybrid-coordination.md](references/hybrid-coordination.md). New multi-shot staged projects with `workflow.handoff_model: prepared_prompt_to_shot` hand each shot a complete initial prompt, and that shot conversation handles its own prompt, image and video-prompt reviews through delivery. Existing projects without this marker keep their original coordinator-led prompt approval and video-prompt route; do not silently convert them. Explicit fast-mode or direct-generation requests stay in the current conversation.
- Default storyboard-making requests, including “生成分镜图” and “视频分镜图”, to `storyboard_and_video_prompt`. After the user approves the storyboard image as usable, automatically draft the matching video prompt and continue to its review. Use `storyboard_only` only when the user explicitly says they do not want a video prompt, such as “只要分镜图” or “不要视频提示词”. Scope determines completion.
- Default to staged review: creative decisions → image → video prompt. Ordinary “生成分镜图” does not waive review.
- Explicit “直接生成 / 不用确认 / 跳过流程 / 跳过审核 / 无需审核 / 只生成就行 / 一次出完 / 合并审核 / 快速模式” permits fast mode with combined final review. Record `set-mode ... fast --reason` for each shot. Fast mode changes review cadence, not delivery scope; keep the default combined delivery unless the user separately declines the video prompt. Ordinary “生成多张分镜图” is staged, not fast.

## Brief and references

Defaults: one image, 9:16 canvas, 2×2 equal panels, 4 seconds, 0–1 / 1–2 / 2–3 / 3–4 seconds, top left → top right → bottom left → bottom right, 1080p target, no dialogue or narration. Minimum duration is 4 seconds; typical range is 4–10 seconds. Preserve approved timing, including valid custom ranges.

Before writing technical prompts, determine whether the user wants a story, a product showcase, or both. Recommend a use context and one primary selling point per image from verified product facts; ask about missing capabilities rather than inventing them. If the requested count cannot be supported without repetitive or unsupported claims, discuss priorities, more product information, or a larger set with the user. A showcase may use packaging, structure, details and function without a character story. For new multi-shot staged projects, the coordinator plans all images and completes their initial technical prompts before choosing concurrency or creating shot tasks; read [hybrid-coordination.md](references/hybrid-coordination.md).

In staged mode, propose one recommended design, then confirm each image in a short exchange showing its context, primary selling point, and four one-sentence panel beats. For a continuous video, first give one sentence describing the overall progression. Vary shot scales by narrative or display purpose; default to at least three scales across four panels, allowing a documented exception. Each panel should add an action, product state, or new information. Avoid near-identical openings and endings, repeated unboxing, and the same action arc across images; an intentional bookend needs a visible change. Repeated core selling points need different evidence and user confirmation unless the user already asked to emphasize them. Save the whole approved design in `content-plan.json` before concurrency selection or generation. An explicit fast request skips visible creative checkpoints, not this internal planning.

For one image, the current conversation writes and checks the technical prompt. For new multi-shot staged projects, the coordinator writes every initial complete `storyboard-prompt.md` and matching shot content, checks each prompt against its confirmed design and the whole batch, then asks about concurrency. The receiving shot conversation uses the saved prompt rather than drafting it again. For **each staged shot**, the conversation responsible for prompt review shows the concise four-panel review and links the saved prompt file; the new handoff model assigns this and all later local reviews to the shot conversation. The full prompt must be a technical extension of the plan, with identical core panel descriptions. Wait for explicit confirmation of this shot and prompt version after both are shown. An earlier design confirmation, project-wide direction, concurrency choice, or silence is not prompt approval.

Bind creative confirmation with `prepare-design-review` → show this shot's short design → `approve-design --review-id ... --confirmation ...`. Editing confirmation text alone is not approval. Explicit fast requests use the same internal version binding without a visible design checkpoint. In the new multi-shot handoff, the coordinator records `check-prompt-plan --note ...` for every initial prompt before concurrency selection; a shot conversation rechecks its own later local revision. These commands are internal bookkeeping, not additional user questions; see [execution.md](references/execution.md).

Each formal design or prompt submission gets a separate review ID, even when resubmitted content is identical. After withdrawal, show the resubmitted version and obtain its own confirmation; never reuse the withdrawn reply. Do not resubmit an unchanged valid review merely because a task resumed, or repeat a still-valid approval.

Stabilize photos under `sources/` using `add-source`. Directly embed original references with absolute local Markdown paths, followed by image IDs and narrow roles. Product photos control identity, structure, color, material and accessories; format images control only layout, photography and labels. Never invent a missing format image. Contact sheets are optional when requested or direct embeds cannot be displayed.

Priority: explicit user text → product reference → scene/light reference → action/composition reference → defaults. Do not invent unseen structures or functions. Substitute another angle or material detail if opening or hand operation is unsuitable.

## Mandatory saved prompt

Every generation requires `shots/<shot-id>/storyboard-prompt.md`, broadly following the user's template in [prompt-templates.md](references/prompt-templates.md). Read that reference for every prompt. Include actual reference roles, layout, photography, four timed states, product constraints, labels and output requirements.

Before staged approval, save the complete prompt and matching `shot.json` review style, selling point and four panels. In a new multi-shot handoff, the coordinator saves these initial files before any child starts; after creation it registers the child's real thread/host identity. Only then does the assigned shot conversation run `prepare-prompt-review`, show its concise plan in that conversation and link the existing prompt file. Do not rewrite a valid handed-off prompt merely because the shot task started, or rebuild a still-valid review when it resumes. Only after the user's subsequent confirmation, run `approve ... storyboard_prompt --review-id ID --confirmation "user reply"`. The command cannot read chat or determine whether the reply was genuinely scoped to this review; the agent must check that. New or changed creative content requires a fresh review. Fast mode keeps its separate explicit authorization.

Populate four panel records, camera plan, product constraints and `sequence_type` (`continuous` or `cuts`) in `shot.json`. Continuous actions must physically connect; different views may use explicit cuts. Do not force opening, hand use, macro details and full-product framing into an implausible single four-second camera move.

After prompt approval or fast-mode authorization, run `preflight <project> <shot-id>` immediately before every image-generation call. Multi-image staged shot tasks must also pass their own `--thread-id`; if registration includes a host, pass the matching `--host-id` too, as described in [execution.md](references/execution.md). It checks saved inputs and reserves one new version. Use the saved prompt for that call. If it fails, do not call generation. Checks cover files, hashes, references and workflow state; the agent still checks prompt quality and visually inspects images.

The saved prompt describes the labeled deliverable. Normally retain its content and append an execution instruction: “Generate clean four-panel artwork without labels or timestamps; reserve label-safe space for later exact typesetting.” Save the actual tool input as `generation-prompt-vNN.md`. If the user explicitly requests generated labels, follow that and do not add duplicate labels afterward.

## Generate and review

1. Staged: resolve creative choices, save the complete prompt and shot data, run `prepare-prompt-review`, show its short plan and a clickable link to the full prompt, wait for confirmation, then record `approve ... storyboard_prompt` with the current review ID and the user's confirmation. Fast: save the internal prompt, record `set-mode ... fast --reason`, then enter `running`.
2. Run preflight. Generate one image with the image-generation skill and save the allocated `storyboard-vNN.png`. Inspect exactly four panels, product identity/count, structures, hands and action plausibility.
3. For clean art, split the verified grid with the layout helper, populate panel `image` paths and compose `storyboard-review-vNN.png`. Inspect labels and cropping. For directly generated labels, inspect them and save the reviewed image under that review filename. See execution.md.
4. Set `qa.result` to `pass` or `pass_with_notes` only after visual inspection. Severe defects enter failure state and require the user's retry decision. Never retry automatically.
5. Staged: enter `storyboard_review_pending`, which records an artifact review ID; present image and QA, then wait. Approve with that ID and the user's subsequent confirmation to freeze the image. Default combined delivery automatically continues to `video_prompt_pending`; save `video-prompt.md`, enter `video_prompt_review_pending`, present and wait for approval of that recorded version. In a new multi-shot handoff, the same shot conversation does this after its active generation slot is released; no routine coordinator return or new registration is needed for video review. Only an explicitly requested image-only delivery completes after storyboard approval.
6. Fast: save image and QA, plus a pending video-prompt draft only for combined scope. Enter `review_pending` to record the package version, then present it. `approve ... review_package --review-id ID --confirmation "user reply"` freezes and completes. Do not describe a pending image as approved.

All new image, video-prompt and package approvals require the artifact review ID and actual confirmation. Changed video text clears its pending review; after the requested edit, use `prepare-artifact-review` and show the new version before approving. Fast video-only revision keeps the image and does not run preflight. These are internal records for the existing user checkpoints, not new questions. See execution.md for old pending projects.

While an image or fast package awaits approval, save a QA-only update to add or correct inspection notes without changing the image. A changed QA clears the pending review: resubmit and show the image with the updated notes at the same checkpoint, without preflight or regeneration. A recorded `failed` result instead stops the shot in its existing failure state and requires the user's next decision. This does not open QA editing for approved images in staged video review or completed work; see execution.md.

Do not automatically submit paid video generation. Video prompts use the matching storyboard as `@Image1`, not an exact first frame, read its panels in order and ignore labels/grid/timestamps. Match the approved sequence type, timing, camera, constraints and actual uploaded image numbering.

## Changes, failures and writes

- Changing prompt, reference, timing, brief or shot plan makes the old binding stale. Use `revise ... storyboard_prompt --reason`, edit, then reapprove in staged mode. Fast mode still needs recorded authorization.
- Changing a creative assignment also needs a fresh version-bound design confirmation (or the recorded explicit fast request). In the new handoff, a shot conversation may handle a user-requested change confined to its own shot: `revise ... storyboard_prompt`, update only its entry in the shared content plan through a fresh whole-file content revision and merge, then renew design confirmation, plan check and prompt review in that same conversation. Do not edit other entries or silently make global/cross-shot changes. Other shots' incomplete drafts do not block this shot; shared content type, relationship, brief or settings changes can affect multiple shots. Never bypass a stale creative approval by removing `content_plan_required`.
- Explicitly requested new attempts from review/failure use `retry ... --reason`. Reopen approved images with `revise ... storyboard --reason`; staged video-only changes use `revise ... video_prompt --reason`. Preserve all old versions and approval history. Failure phase controls retry destination.
- Never manually edit statuses/approvals. Save mutable project content via `content-revision` and `save-content --expected-hash` using an owner-local draft; see execution.md. These writes share the workflow lock and reject stale edits. Recovery touches only this operation's writes and stops on conflicting external changes. Do not remove a lock/journal to bypass a busy command or recovery conflict.
- For user-requested swaps or grouped creative changes, stop/release the affected tasks, run `revise-designs ... --reason`, then update and reconfirm those designs. Retired design records remain in history but no longer reserve their old action arcs.
- A pilot authorizes at most 1–2 distinct shots for that round, not a rolling queue. Releasing or completing them does not authorize more shots; ask how to continue and record the new launch choice with `set-concurrency --reason`.
- Preflight also enforces the current launch choice and matches the caller's task identity to the active registration for multi-shot staged generation. Use the task's own identity supplied from its creation result, never copy the current owner from `project.json`. Image approval releases the active slot but keeps the same shot conversation and identity for video review; no active slot is needed for a finished image or its video prompt. Any later image regeneration must again have a valid active registration and permission in the current all/pilot round; a prior round's shot does not bypass a newer pilot choice. Single and fast shots need no task.
- Do not reset an unfinished generation through revision. Wait for its result and record QA, or record its actual failure. A completed image for the allocated version with passing QA allows user-requested prompt/design revision even if the inputs have since changed; preserve the old image, but do not approve it as satisfying the new requirements. Approval and further generation still require valid current inputs and authorization. A recorded failure does not cancel an external tool call; never mark failure just to bypass this guard.
- Delivery scope is project-wide. A pending prompt review must be withdrawn before an early scope change; this is allowed only when no shot has prompt/artifact approval or generation history and all shots are back in drafting. Returning to drafting does not erase approval or image history. Mid-project scope conversion remains unsupported: explain the limitation and ask how to proceed, without altering hashes, discarding history, or regenerating images to bypass it.
- Schema-v3 projects need explicit `migrate`, which backs up changed manifests and resets unbound approvals to pending. Old v4 approvals lacking hashes need revision and renewed approval before further generation; never fabricate retrospective approval.

See [schema.md](references/schema.md) for fields and [strict-mode.md](references/strict-mode.md) for staged review. These commands cannot intercept an agent that directly calls a generation tool without using them; mandatory preflight remains an agent execution requirement.
