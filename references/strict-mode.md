# Staged review

Read [execution.md](execution.md) for commands, artifacts, revisions and recovery.

1. Determine quantity (default one) and scope (storyboard plus video prompt unless the user explicitly declines the video prompt). Keep one image here.
2. Resolve story/showcase intent, verified product facts and selling-point priorities. For new creative-plan projects, save the whole batch design with all six-column details in the existing beats/scales and check panel purpose, within-grid progression and global repetition. Read [creative-review-template.md](creative-review-template.md), show the overview and each four-row table, then get one scope-clear batch confirmation. Prepare each necessary design review before presentation and record the actual reply against its matching ID. After approval and shared/source preparation, record the default all launch without another question, or the user's explicit pilot, then create and register same-project children. No technical prompt is needed yet. Explicit fast mode skips visible creative review, not internal planning.
3. For one image, the current conversation writes, checks and reviews the prompt. In `creative_plan_to_shot`, each child reads the batch context and its complete approved design, writes its first `storyboard-prompt.md` and shot fields, and records `check-prompt-plan`. After real identity registration it prepares the prompt review, presents [storyboard-prompt-review-template.md](storyboard-prompt-review-template.md) with reference previews, the six-column current summary, differences and complete file link, then waits for this version's confirmation. Approve with its review ID before generation; the same child owns image/video work and delivery. Existing valid drafts, reviews and approvals are not rewritten on resume. Creative approval is not prompt approval.
4. Run `preflight` immediately before generation. Use its version, generate, inspect, label and save the review image.
5. Enter `storyboard_review_pending` to record its artifact review ID, present image and QA, and wait. Approve with this ID and the user's subsequent confirmation to freeze the image and metadata; image-only scope completes here.
6. After the user approves the storyboard as usable, default combined scope automatically saves `video-prompt.md`, enters `video_prompt_review_pending` to record its review ID, and presents it for approval with that ID and confirmation. In the new multi-shot handoff the same shot conversation owns this stage; a legacy unmarked multi-shot project keeps coordinator ownership, while single/fast requests remain in the current conversation. Only an explicit image-only scope completes at storyboard approval.

Do not infer approval from silence, a project-wide direction, or a concurrency answer. The CLI verifies content bindings but cannot verify the meaning or timing of the user's reply; check both before recording approval. Previously approved legacy projects remain readable; new or materially changed content requires this staged review. Explicit fast-mode requests use the alternative workflow in SKILL.md.

Use the existing design review commands per shot even when one reply approves the displayed batch; no new approval stage is added. The technical-prompt author runs `check-prompt-plan` before prompt review: current conversation for single/fast, child for creative handoffs, coordinator for older prepared initial prompts. Both child-owned modes handle later local revision checks. Global changes need coordination; another shot's unrelated draft does not invalidate this one. Editing any approved beat subpart or scale stales creative approval; changed technical inputs stale plan/prompt approval.

Compatibility: existing `prepared_prompt_to_shot` projects keep their previous creative cadence, coordinator-written complete initial prompts and checks, and an explicit all/pilot question before child creation; children review the handed-off prompt locally without redrafting. Unmarked projects retain child drafting followed by coordinator checking/approval and video prompts. Neither route is silently converted or forced to rewrite existing designs into the new presentation format. Single and explicit fast execution remain in the current conversation.

Creative, prompt and image revisions go through `retry` or `revise` with user reasons. A QA-only correction while the image awaits approval uses `save-content`, preserving the image; minor changes require the updated notes to be shown again, while `failed` stops the shot in its existing failure state. Ordinary status changes cannot restart generation. Approved files must still match their hashes.

After requested edits invalidate an artifact review, use `prepare-artifact-review` and show the current version before obtaining a new reply; do not attach an old reply to a fresh ID. Withdrawn designs and prompts also need a new submission and reply, even if their content is identical. Wait for an unfinished generation's actual result/failure before revision; a completed allocated image with passing QA can enter prompt/design revision even if its inputs have since changed, without treating it as an approved new result. See execution.md for failure recovery and the current restriction on mid-project delivery-scope changes.

Save drafted content with `content-revision` / `save-content --expected-hash` as described in execution.md. A current prompt review means wait, not continue drafting or regenerate its ID. In a new-model shot conversation, a user-requested creative change confined to that shot may follow `revise storyboard_prompt`, update only its own `content-plan.json` entry by whole-file read/merge/CAS, and renew design, plan check and prompt review locally. For grouped/global changes, coordinate and use `revise-designs` where appropriate; reconfirm only affected shots. Image approval releases the active slot while the same child continues video review without re-registering. Later image regeneration still requires current-round pilot/all authorization and an active identity. Pilot completion authorizes no additional shot until the user's continuation choice is recorded.
